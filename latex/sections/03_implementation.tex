\section{Implementation Decisions and Trade-offs}

\subsection{Connection reuse vs. a fresh connection per packet}

The HTTP/2 generator opens one \texttt{httpx} client with HTTP/2 enabled and
keeps it open for the whole run, firing several requests at once over that
single connection to actually use multiplexing rather than just claiming to.
The QUIC generator does the same thing for the same reason: a QUIC handshake
costs at least one extra round trip, and if the generator reconnected for
every request that handshake cost would swamp the latency numbers and make
QUIC look artificially slow next to HTTP/2 and MQTT, both of which also keep a
connection open.

The TCP/UDP generator does the opposite on purpose. For every single TCP
packet it opens a new connection, sends, and closes it again. This was not an
oversight. A fresh connect/close cycle produces a real SYN, SYN-ACK and FIN
sequence in the capture, which is exactly what is needed later for the
Failure Visibility analysis and for telling raw TCP apart from the
application-level protocols in a protocol hierarchy view.

\subsection{Mode and pattern as two separate knobs}

The TCP/UDP generator splits "what does a packet look like" from "how is it
paced over time". \texttt{mode} controls size and base interval: normal mode
uses a fixed 512 bytes every 100 ms, stealth mode draws a random size between
64 and 1400 bytes with Poisson-distributed timing. \texttt{pattern}
independently controls the sending cadence on top of that: constant, periodic
burst, or an extra random gap. Keeping these two orthogonal made it possible
to test, for example, stealth-mode sizing combined with a burst cadence, which
would not have been possible if mode and pattern were the same setting.

\subsection{The Poisson pattern on every protocol, not just one}

The assignment only asks for a random, Poisson-distributed pattern somewhere
in the system. This implementation puts it on all four generators using
\texttt{random.expovariate(1/interval)} (or NumPy's exponential distribution
for the TCP/UDP generator), which produces exponentially distributed gaps
between sends with the same average rate as the constant pattern. The reason
to extend it everywhere was to be able to show one single Wireshark capture
where HTTP/2, QUIC and MQTT all use Poisson timing at once, alongside TCP/UDP
stealth mode, rather than only ever demonstrating it on one protocol.

\subsection{Warmup and cooldown double as the ramp pattern}

Rather than building a separate "ramp" mode per protocol, the warmup and
cooldown periods are handled once, centrally, in the controller. A function
called \texttt{\_ramp\_rates()} steps every generator's rate field linearly
from zero up to its configured target over the warmup window, and back down
to zero over the cooldown window, sending the new value through the normal
PATCH endpoint at each step. This single mechanism satisfies both
requirements at once: the warmup/cooldown behavior the assignment asks for,
and the "ramping" sending pattern, since the gradual change shows up as a
slope in a Wireshark I/O graph either way.

\subsection{Adaptive Control}

The controller can run an autonomous control loop, either because a YAML
phase turns it on or because it was switched on manually. Every few seconds it
checks each generator's error rate, and where reported its latency, against
configurable thresholds, and scales the rate up or down by a multiplier
bounded on both ends. This goes past the baseline requirements, but it ties
directly into the resilience patterns covered in the course: the system reacts
to an injected failure on its own, without anyone touching a slider.

\subsection{Why the MQTT generator subscribes to its own topics}

The MQTT generator subscribes to every topic it publishes on. This looks
redundant, but it serves a specific purpose. When a client subscribes to a
topic, the broker sends a copy of each published message back to that client.
This fan-out step is normally invisible to the publisher, because it happens
inside the broker. By subscribing to its own topics, the generator makes the
broker's delivery work show up as real network packets between the broker and
the client. The result is that a Wireshark capture on the broker's network
interface shows both the inbound PUBLISH and the outbound delivery -- roughly
doubling the visible packet count -- which makes the QoS overhead much clearer.
With QoS~2, each message goes through a four-step handshake
(PUBLISH, PUBREC, PUBREL, PUBCOMP) in each direction
\cite{mqtt5}. Without the subscription, only the inbound half would appear.
The trade-off is that the generator handles more messages than a
pure-publisher would, which slightly inflates CPU and memory usage at
high publish rates.

\subsection{Using an unmodified Mosquitto image}

The MQTT broker runs as the official \texttt{eclipse-mosquitto} image
without any changes \cite{mosquitto}. A modified broker could export
Prometheus metrics, report per-topic throughput, or push data to the
metrics collector directly. We chose not to do this for one reason: the
project aims to evaluate traffic under realistic conditions, and any custom
build of Mosquitto would move the broker away from a standard deployment.
The trade-off is that the system has less visibility into broker internals.
Queue depths, retained message counts, and session state are not reported
anywhere in the dashboard. This information would be useful for stress
tests, but it would require either a custom Mosquitto plugin or a separate
sidecar exporter. We accepted the gap and rely instead on the client-side
publish-rate and error-rate counters that the MQTT generator already tracks.

\subsection{The TCP/UDP sink does not report to the metrics collector}

The TCP and UDP target services (the sink containers) accept incoming
connections and packets but do not send any data back to the metrics
collector. The generators report their own send counts and error rates, so
the overall picture of packet volume is still captured. The decision to keep
the sink silent was deliberate. A sink that posts metrics over HTTP creates
its own TCP connections. In a Wireshark capture those connections look
identical to application traffic and make it harder to identify RST flags
and half-open connections from the actual test traffic. Keeping the sink
silent ensures that every TCP connection visible in the capture belongs to
the generator, which makes failure analysis cleaner and easier to explain
during a presentation.

\subsection{Stateless burst timing in the HTTP/2 generator}

Many traffic generators implement periodic bursts with a background timer
thread: sleep until the burst window, send, sleep again. We used a different
approach. The HTTP/2 generator computes the current position in the burst
cycle from the wall clock using a modulo operation:

\begin{verbatim}
  t = time.monotonic()
  phase = t % burst_interval
  in_burst = phase < burst_duration
\end{verbatim}

This makes burst timing stateless. The generator does not store any
information about the last burst. If the container is restarted, or if
the asyncio event loop experiences a delay, the burst schedule stays
correct because it is derived entirely from the current time. A
\texttt{sleep()}-based approach would drift after any interruption
and produce bursts at the wrong times relative to other generators
running in parallel. The trade-off is that very short burst intervals
(less than a few hundred milliseconds) become unreliable because the
event loop's own scheduling granularity is larger than the interval.
For the burst intervals used in the profiles (10 seconds or more),
this is not a concern. A similar argument for stateless, time-derived
scheduling appears in the context of distributed workload generation
tools \cite{ditg}.

\subsection{Dashboard polling and input debouncing}

The dashboard polls the controller's \texttt{/status} endpoint every two
seconds using \texttt{fetch()}. An event-driven alternative, such as a
WebSocket or Server-Sent Events connection, would deliver updates
immediately rather than with up to two seconds of delay
\cite{rfc6455}. We chose polling for two reasons. First, it requires no
persistent connection state on the server side, which means the controller
stays stateless between requests and is easier to restart without
affecting the dashboard. Second, the poll interval of two seconds matches
the rate at which the generators update their own internal state, so a
faster poll would not produce more useful data.

The rate sliders in the dashboard are debounced with a 400~ms delay.
Without debouncing, dragging a slider from 10 to 100 would fire roughly
90 PATCH requests in quick succession, each of which triggers an HTTP call
to the controller and a forwarded call to the generator. That sequence of
requests can arrive out of order and leave the generator at an
intermediate rate rather than the intended final value. The 400~ms delay
means only the last value sent after the user stops moving the slider
reaches the generator. The trade-off is a visible lag between the user's
hand and the generator's response, but this is acceptable in a lab
environment where the goal is to set a target rate, not to achieve
continuous real-time control \cite{Fielding2000}.
