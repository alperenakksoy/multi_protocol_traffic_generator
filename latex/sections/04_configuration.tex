\section{Configuration Format}

\noindent The controller reads multi-phase YAML profiles from the \texttt{config/} folder.
Each profile defines how traffic should evolve over time.
This makes it possible to run a full experiment, including warmup, several distinct
traffic phases, and a cooldown, with a single command~[cite: 1].

\subsection{Profile Structure}

\noindent Every profile starts with a \texttt{global} block that sets the warmup and cooldown
durations in seconds.
Below that is a list of \texttt{phases}.
Each phase has a name, a duration, and a \texttt{protocols} block with one entry
per protocol that should be active during that phase~[cite: 1].

\noindent The structure follows this pattern:

\begin{verbatim}
global:
  warmup:   30
  cooldown: 30

phases:
  - name: example_phase
    duration: 60
    protocols:
      http2:
        rate: 50
        payload_size: 2048
      mqtt:
        rate: 30
        qos_distribution: {0: 60, 1: 30, 2: 10}
\end{verbatim}

\noindent Only protocols listed inside a phase are active during that phase.
A phase that omits \texttt{quic}, for example, leaves the QUIC generator at its previous
rate rather than stopping it.
The controller applies each phase by calling the PATCH endpoint on every listed generator
at the start of the phase~[cite: 1].

\noindent Field names in the YAML must match the generator's Pydantic model exactly.
Extra keys are silently ignored for forward compatibility, but a misspelled field has
no effect at runtime.

\subsection{Adaptive Control Block}

\noindent Any phase can include an optional \texttt{adaptive\_control} block.
When this block is present and \texttt{enabled} is set to true, the controller starts
its autonomous control loop for the duration of that phase~[cite: 1].
The loop checks each generator's error rate and latency every \texttt{check\_interval}
seconds and applies a rate multiplier to scale traffic up or down automatically.

\noindent The block exposes two threshold groups: \texttt{scale\_up\_threshold} and
\texttt{scale\_down\_threshold}.
Each group specifies limits for error rate and latency.
The multiplier is bounded by \texttt{min\_multiplier} and \texttt{max\_multiplier}
to prevent runaway scaling in either direction~[cite: 1].
A minimal adaptive control block looks like this:

\begin{verbatim}
adaptive_control:
  enabled: true
  check_interval: 5
  scale_up_threshold:
    error_rate_max: 0.0
    latency_max_ms: 100
  scale_down_threshold:
    error_rate_min: 0.05
    latency_min_ms: 250
  scale_up_factor:   1.2
  scale_down_factor: 0.5
  min_multiplier:    0.1
  max_multiplier:    5.0
\end{verbatim}

\subsection{Shipped Profiles}

\noindent The project ships 14 YAML profiles split into two categories.
The first category covers protocol-behavior presets and is directly accessible via the
dashboard's \textbf{Preset} button row~[cite: 1]:

\begin{itemize}
  \item \texttt{balanced.yaml} -- equal load across all four protocols with three phases:
        constant baseline, stealth mode with Poisson timing, and adaptive control.
  \item \texttt{http2\_heavy.yaml} -- HTTP/2 dominates, with a burst phase and concurrent
        streams pushed to their limit.
  \item \texttt{mqtt\_heavy.yaml} -- three phases that compare QoS~0, QoS~2, and a mixed
        QoS distribution side by side.
  \item \texttt{quic\_heavy.yaml} -- QUIC baseline, then high-throughput with 0-RTT, then
        a burst phase to measure connection reuse under load.
  \item \texttt{tcpudp\_heavy.yaml} -- alternates between TCP-dominant and UDP-dominant
        phases, ending with a mixed transport burst.
  \item \texttt{burst\_mode.yaml} -- all protocols burst simultaneously at different
        intervals, creating irregular compound spikes in the I/O graph.
  \item \texttt{fault\_injection.yaml} -- steps fault rates from 5\% up to 50\% and
        ends with a recovery phase driven by adaptive control.
  \item \texttt{adaptive\_only.yaml} -- adaptive control is active from the very first
        phase, with no manual rate changes at all.
\end{itemize}

\noindent The second category contains use-case scenario profiles, accessible via the
\textbf{Scenarios} button row on the dashboard~[cite: 1]:

\begin{itemize}
  \item \texttt{iot\_sensor\_farm.yaml} -- simulates a fleet of IoT sensors with
        MQTT-heavy, low-payload traffic and a QoS~2 alarm phase.
  \item \texttt{video\_streaming.yaml} -- models an HTTP/2 and QUIC content delivery
        scenario with an evening-peak burst and a lossy-network phase.
  \item \texttt{microservices\_api.yaml} -- a read-heavy baseline followed by a write
        spike and a cascading-failure phase that activates adaptive control.
  \item \texttt{network\_stress\_test.yaml} -- a four-phase ramp from zero to full load,
        then deliberate overload, then auto-recovery.
  \item \texttt{smart\_city.yaml} -- mixed sensor and video traffic with an emergency
        event phase that shifts QoS distribution and activates adaptive control.
\end{itemize}

\noindent A fifteenth profile, \texttt{demo\_showcase.yaml}, is included solely for
live demonstrations and is not exposed through the dashboard preset buttons.

\subsection{Runtime Configuration}

\noindent Configuration is not locked to the YAML once the system is running.
Two REST endpoints allow live changes without restarting any container~[cite: 1]:

\begin{itemize}
  \item \texttt{POST /config/load} sends a profile name to the controller.
        It reads the YAML, updates the internal phase schedule, and applies phase one
        immediately if the system is already started.
  \item \texttt{PATCH /generator/\{name\}} forwards any subset of the fields from
        Table~\ref{tab:config-fields} to a single generator.
        The generator applies the change within its next send cycle.
\end{itemize}

\noindent The dashboard wraps all configurable fields in sliders, toggles, or text inputs.
Every input calls one of these two endpoints.
Rate sliders are debounced with a 400\,ms delay so that dragging quickly does not
flood the controller with requests~[cite: 1].
Dropdown menus for pattern and mode take effect immediately on change.
